= Software Factory Application Split: Implementation Plan
:toc:

== Status and Objective

Planning complete; implementation has not started. This document captures the conversation's final scope for the next implementation agent. It is not a record of implemented functionality.

Build a separately runnable Software Factory application with Next.js and React. The application owns authentication, teams, memberships, and daemon connections in its own database. It connects to multiple Go daemons running in independent sandboxes and displays and controls their tasks.

Keep application and daemon in this repository initially. Separate their runtime, persistence, and release/build responsibilities; splitting repositories is not required.

== Confirmed Decisions

* Use Next.js with a React migration. The user does not want to maintain Vue.
* Next.js supplies both the UI and application backend. Do not introduce an additional Go application backend.
* Start self-hosted, rather than targeting a serverless hosting platform.
* The application has its own database for application-owned state.
* Support GitHub and Google login initially.
* Registration is invite-only, with an explicitly configured initial owner. There is no public signup or first-login-wins administrator bootstrap.
* Daemons remain authoritative for tasks and execution; the application displays daemon tasks and forwards authorized actions.
* Support multiple independently running sandbox daemons.
* Retention is deferred, not rejected permanently.

== Proposed Implementation Defaults

These were recommended during planning, not individually mandated by the user. Use them unless implementation research reveals a concrete problem; explain material departures.

* PostgreSQL for application persistence.
* Better Auth for provider login, sessions, and membership/invitation support.
* Use Better Auth's organization tenant as the product's Team. Avoid adding a separate organization plus nested-team hierarchy.
* Each daemon registration belongs to exactly one Team initially. Cross-team sharing is outside the initial scope.
* Owners/admins manage membership and connections; members can browse and operate the Team's tasks. Define explicit permissions rather than deriving authorization from UI visibility.
* Copyable, email-bound invitation links initially, avoiding an SMTP dependency.
* Docker Compose for the Next.js application and PostgreSQL, with persistent database storage. Daemons run independently, not as mandatory dependencies of the application's startup.
* Preserve the existing UI's workflows and visual language during the React migration.

== Target Architecture and Ownership

[source,text]
----
Browser
   |
Next.js application
   |-- React UI
   |-- Authentication and sessions
   |-- Teams, memberships, invitations, permissions
   |-- Daemon registry and authorized HTTP/SSE access
   |-- PostgreSQL application database
   |
   +-- Go daemon in sandbox A: execution + local task database/files
   +-- Go daemon in sandbox B: execution + local task database/files
----

The browser talks to the application, not directly to arbitrary daemon addresses. Provider secrets and daemon credentials stay server-side.

Application persistence covers users, provider accounts, login sessions, Teams, memberships, invitations, one-time bootstrap state, daemon registrations, and application preferences as needed. An authentication login session is distinct from a daemon Task Session.

Daemon persistence continues to cover tasks and child Task Sessions, repositories, attempts, branches, events, interventions, results, checks, local logs, artifacts, and workspace snapshots. No task database migration to PostgreSQL is part of this split.

Use Server Components for suitable initial reads, and Client Components for interactive controls, forms, selection, and live events. No requirement to force every read through RSC or use experimental caching features. Team-private data must not leak through shared caches.

== Authentication and Authorization Contract

=== Initial Owner

* Configure the initial owner server-side, for example through `INITIAL_OWNER_EMAIL`; the exact environment-variable name is an implementation detail.
* Grant bootstrap ownership only after GitHub or Google proves ownership of the configured verified email. An OAuth login or profile email string alone is insufficient proof. Fail closed if verification cannot be established.
* Persist bootstrap completion in PostgreSQL and make concurrent bootstrap attempts safe. Changing configuration later must not silently create another owner.
* The initial owner can create the first Team and invite members. Bootstrap status does not grant permanent access to every Team or daemon; normal membership checks still apply.
* Missing or invalid bootstrap configuration must have an actionable setup error, not fall back to public signup.

=== Login and Invitations

* Existing accounts may sign in through their linked providers; Team resources require current membership.
* Block unauthorized new account creation in the server-side OAuth/signup path, not merely by hiding signup buttons.
* An invited new user must authenticate with the matching verified email. Invitation possession alone does not establish membership.
* Invitations identify the Team, recipient email, assigned role, inviter, expiration, revocation, and acceptance state.
* Use opaque, unguessable invitation identifiers/tokens, enforce expiration and single use, and consume membership grants transactionally.
* Team owners/admins may issue and revoke invitations within their authorized Team and role-grant limits.
* Account creation and invitation acceptance must have a defined failure/retry path. A rejected, revoked, or raced invitation must never grant membership or bypass the registration gate.
* Keep GitHub/Google account linking explicit and authenticated. Do not silently merge accounts solely by equal email strings.
* Request only provider permissions needed for identity. GitHub sign-in does not grant the sandbox repository credentials or permissions.

Better Auth has Next.js, provider, and organization support, but verify the selected release's actual signup hooks, invitation semantics, email verification, and account-linking defaults before relying on them. Reuse its mechanisms where they meet this contract; test the full OAuth-to-invitation path.

=== Resource Access

* Validate session and current membership for every protected server read, action, route handler, file response, and stream. Redirect middleware and active-Team selection are not authorization.
* Scope daemon lookup by authorized Team before contacting an upstream. An attacker-supplied daemon/task ID must not bypass tenancy checks.
* Apply role checks to invitations, membership changes, connection management, and execution actions. Prevent privilege escalation and accidental loss of the last owner.
* Membership removal must revoke resource access, including long-lived streams within a defined bounded revalidation interval. Test it.
* Validate mutation origin/CSRF protections and configure trusted application origins explicitly.

== Daemon Connectivity Contract

* Store a stable application-side daemon registration ID, Team ownership, display name, endpoint, and credentials. Qualify task identity and routes by daemon ID plus task ID; never by task ID alone.
* Add daemon identity to the connection handshake, or an equivalent explicit replacement check, so reusing an endpoint does not silently associate a different sandbox with the old connection.
* Add real application-to-daemon authentication for reads, mutations, and streams. The current daemon mutation token is not remote authentication.
* Use HTTPS or an explicitly trusted local/private tunnel. Preserve safe loopback defaults; configurable remote binding must not enable unauthenticated public access.
* Keep browser cookies and OAuth tokens out of upstream requests. Use only the daemon credential and explicitly selected headers.
* Restrict configurable upstream destinations using deployment-controlled policy. Private sandbox addresses may be legitimate, but connection management must not become an arbitrary SSRF proxy. Address redirects and DNS changes as well as initial URL validation.
* Keep stored credentials protected at rest, redact them in logs and errors, and return no secrets to clients. Choose the smallest suitable secret-storage approach for the self-hosted deployment.
* Preserve daemon error status/meaning, request cancellation, reasonable timeouts, and SSE flush/reconnect behavior.
* Daemon unavailability must not block unrelated daemons or application login/team management. Display connection errors per daemon and disable actions requiring that daemon.
* Do not queue offline execution commands in this release.

Exact credential provisioning and transport mechanics remain implementation choices. A per-daemon server credential and trusted reachable endpoints are a reasonable first slice. Sandbox provisioning, reverse-connect agents, and automatic tunnel management are not required.

== Repository Starting Points

Re-read source and `git status` before editing; these are navigation pointers, not a substitute for current code.

* `main.go`: daemon startup, SQLite recovery, local root/lock, harness registration, API wiring, embedded Vue assets, Swagger, loopback bind, shutdown.
* `main_test.go`: Swagger and same-origin documentation checks.
* `internal/api/api.go`: task/action routes, mutation-token and origin checks, REST events and SSE.
* `internal/factory/service.go`: task creation and execution, child Task Sessions, task deletion, check logs, prompts, and process ownership.
* `internal/store/store.go`: daemon SQLite schema, transitions, events, lineage, and startup recovery.
* `internal/harness/harness.go`: agent runtime interface, not the remote-daemon interface. Keep these concerns separate.
* `web/src/api.ts`: singleton same-origin client and module-global mutation token.
* `web/src/types.ts`: existing TypeScript request/response shapes; reusable after checking against actual daemon responses.
* `web/src/App.vue`: task/session routing, polling, direct EventSource usage, actions, detail selection, and async state handling.
* `web/src/components/`: task creation, task/artifact rails, artifact viewer, session log, and intervention composer to migrate.
* `web/vite.config.ts`, root and web `package.json`: current frontend build and development wiring.
* `swagger.yaml`: daemon interface description; update with shipped daemon interface changes.
* `CONTEXT.md`, `docs/ARCHITECTURE.md`, `docs/USAGE.md`, `SPEC.md`, `docs/retriable-execution.adoc`: terminology and existing behavior. Older single-host/no-remote constraints do not override the user's application-split decision here.

Current behavior requiring care:

* The daemon binds to loopback. `/api/v1/control` exposes a random per-process mutation token; reads are not authenticated by that token. The token and same-origin checks protect local browser mutations, not remote Team access.
* SSE supports `after` and `Last-Event-ID`. Sequence numbers are daemon-database-wide; per-task gaps are normal. Preserve cursor scope and avoid duplicate display on reconnect.
* Events are not a complete task-state change journal. Keep task/detail refresh rather than assuming SSE reconstructs state.
* Current UI guards often compare only task IDs. React state and stale-response protection must also include Team/daemon selection, with cancellation or request generations.
* Repository paths and artifact paths belong to the daemon filesystem, not the application host or browser. Explain this in the UI; do not read those paths on the application server.
* Task Sessions are child task records, not auth sessions or native agent-session files.
* Deleting a root task can delete its child Task Sessions and task files. Preserve existing behavior without claiming archival safety.

== Execution Sequence

=== 1. Independent Application Foundation

Create a Next.js npm workspace alongside the existing frontend, with TypeScript, application persistence/migrations, environment validation, and test setup. A top-level `application/` directory is a reasonable default; existing root Go layout need not move.

Completion: the application builds and starts without a daemon database, daemon lock, agent executable, or Vue build. The existing daemon/UI still starts as before during migration.

=== 2. Identity and Teams

Implement both providers, database-backed sessions, initial-owner bootstrap, Team creation/switching, membership management, and invitations under the security contract above. Provide login/setup/error states and explicit provider linking.

Completion: an initial owner can create a Team, invite another user, and grant scoped access; an uninvited identity cannot register; tests prove bootstrap and invitation race/replay handling and cross-Team denial.

=== 3. Authenticated Daemon Registration and First Task Read

Add the smallest authenticated Go daemon interface changes required, Team-scoped connection persistence, endpoint policy, health/identity checks, and a server-only daemon client. Route through the application instead of changing browser base URLs.

Completion: one Team can connect two test daemons, read their tasks independently, and distinguish overlapping task IDs; another Team cannot access either connection by guessing IDs. No secrets reach the browser.

=== 4. Actions, Live Events, and Failure Isolation

Support the existing daemon commands, creation/config/model flows, and SSE through authorized application handlers. Handle daemon restarts, credential/token lifetime where applicable, event replay, request cancellation, and revoked access. Reads and commands use the same scoped connection lookup.

Completion: create a draft on the selected daemon, receive its live events, reconnect without duplicate display, and continue using a second daemon when the first is offline. Commands never silently reach the wrong daemon.

=== 5. React Workflow Parity

Migrate task/session creation, lists and navigation, start/approve/pause/resume/abort, feedback and interventions, attempt and branch selection, results, checks, diffs, artifacts, logs, and deletion. Preserve relevant existing action restrictions and stale-plan/branch handling.

Add Team and daemon selectors, combined Team task browsing, daemon-qualified routes, and per-daemon connectivity feedback. Scope recent repository paths and any other client preferences by their actual Team/daemon owner. Clear or cancel old selection work when switching; use explicit offline/unavailable states rather than presenting old live data as current.

Completion: existing workflows and uncommitted UI improvements are represented in React; browser tests cover multi-daemon selection and representative mutations on desktop and mobile.

=== 6. Cutover and Self-Hosted Packaging

After parity, retire Vue and remove the daemon's frontend embedding/build dependency. Keep daemon execution and useful Swagger access. Update workspace scripts, relevant existing usage/architecture docs, Docker/Compose configuration, migrations, and environment examples. Keep secrets out of source control and container images.

Completion: the Go daemon builds without frontend assets; the self-hosted application and PostgreSQL start independently of sandboxes; fresh and existing application databases have a documented migration path; all relevant checks pass.

== Verification Matrix

* Authentication: both providers, logout, session expiration, unauthorized OAuth account creation, unverified/mismatched emails, explicit account linking, and provider/callback failures.
* Bootstrap: absent configuration fails closed, only the configured verified identity succeeds, concurrent first logins are safe, and changed configuration cannot grant a second bootstrap owner.
* Invitations: expiration, revocation, single use, replay/concurrent acceptance, email binding, grant limits, and safe retries after partial failure.
* Tenancy: cross-Team reads/mutations/streams/connections denied, guessed IDs rejected, private data not shared through caches, role escalation prevented, and removed members lose access.
* Connectivity: missing/invalid daemon credentials, unsafe destinations/redirects, redacted errors, two daemons with overlapping IDs, offline daemon isolation, restart/reconnect, and no browser-secret exposure.
* Streaming: cursor forwarding, flush behavior, cancellation, duplicate suppression, and access revocation for open streams.
* React: Team/daemon switching with delayed requests, stale responses/errors/events, creation/config/model scoping, session navigation, commands and interventions, desktop/mobile layouts.
* Packaging: independent application/daemon builds and startup, persistent PostgreSQL volume, migrations, and production environment validation.

Run the repository's declared checks: `go test ./...`, `go test -race ./...`, `npm run typecheck`, and `npm run build`. Update npm scripts to cover the new workspace during migration and the final application after cutover. Add application and browser tests for the acceptance cases above; existing frontend scripts currently have no test runner.

Never claim real GitHub/Google OAuth end-to-end verification without actual configured providers. Automated provider-boundary tests can run without secrets; report external setup blockers separately.

== Deferred Scope and Future Retention

No background synchronization worker, durable task mirror, blob storage, archival exports, archive receipts, sandbox deletion barriers, cross-daemon task migration, global execution scheduler, or sandbox provisioning in the initial release.

The earlier retention discussion remains a future requirement, not acceptance criteria here. If resumed, preserving full history requires more than copying events: existing endpoints omit full raw logs/native sessions and hidden persisted records, artifact paths are not file contents, and some prompt/check files are overwritten. A complete archive must account for these gaps. Controlled deletion and unexpected volume loss have different durability requirements. Do not suggest the initial live application solves either.

== External Setup and Remaining Choices

No unanswered product question blocks starting implementation. Actual deployment requires an application origin, owner email, PostgreSQL connection, authentication secret, GitHub and Google client IDs/secrets, and reachable daemon endpoints/credentials. Obtain these through environment/secret configuration, never committed values.

With the documented Better Auth defaults, OAuth callback paths are `/api/auth/callback/github` and `/api/auth/callback/google`. Verify them against the implemented auth base path before registering providers. Production should use the configured HTTPS origin; local provider setup can use supported localhost callbacks.

Resolve ORM/migration tooling, endpoint allowlisting, credential storage/provisioning, and exact role policy during implementation. Ask the user only if a choice materially changes this scope or trust model. Defer account-recovery tooling and deployment automation beyond the initial safe setup unless required to operate the chosen authentication integration.
