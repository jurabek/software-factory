== Decisions

* Retrying work in a completed Task reopens the same Task.
* A message sent to a running Agent defaults to steering delivery.
* The UI accepts a message only. It cannot override role configuration, except for agent, model, and thinking level selected at Task creation.
* Every Task receives a private Task Workspace when created.
* Workspace snapshots remain until explicit Task deletion.
* The UI uses `Task`; legacy Campaign naming is removed with the clean break.
* The desktop shell has a persistent Task rail, central Task workspace, and contextual Artifact rail/viewer.
* A user may act from any displayed state, Event, Attempt, or Artifact when transition policy permits.
* A state-changing action creates an Intervention and a new attempt or branch. Historical state is never edited in place.
* Artifact messages anchor to immutable source coordinates, not rendered DOM positions.
* Reusable visuals live behind a framework-neutral CSS interface; Vue is an adapter at that seam.

== Terminology

Phase Definition:: An immutable, versioned description of work, its executor, inputs, dependencies, and acceptance policy.

Phase Attempt:: One execution of one Phase Definition revision.

Event:: An immutable observation emitted by a Phase Attempt. An Event is an addressable anchor, not an executable unit.

Artifact:: A versioned output from an attempt, such as a plan, repository snapshot, check result, diff, or review result.

Artifact Anchor:: An immutable Artifact digest plus a canonical text range, source line range, JSON pointer, or whole-block coordinate. It identifies the selected content independently of its rendered HTML.

Intervention:: A persisted human message anchored to an Event, Artifact, or Phase Attempt.

Execution Branch:: An immutable lineage of attempts. Retrying or revising historical work creates a new branch from the selected attempt.

Agent Session:: The harness conversation used by an Agent attempt. It is not a workflow step.

Task Workspace:: The private filesystem root created for one Task. It owns that Task's repository materializations, attempts, snapshots, sessions, and artifacts.

Workspace Snapshot:: A content-addressed repository state used as an attempt input or produced as an attempt output.

== Guarantees

The factory guarantees reconstructable inputs and safe re-execution. It does not guarantee byte-identical Agent output because model providers and external tools may be nondeterministic.

Every attempt records:

* Phase Definition ID, revision, and digest
* input Workspace Snapshot digest
* dependency Artifact IDs and digests
* exact rendered system and user prompts
* accepted Interventions and delivery order
* harness name and version
* provider and model IDs
* thinking level
* harness name and version (agents use all available harness tools)
* Pi version and Agent Session coordinates
* working directory, command arguments, relevant environment, and timeout
* start and end timestamps, status, error, usage, and cost
* output Workspace Snapshot and Artifact digests

History is append-only:

. A Phase Attempt is never reset or overwritten.
. A Phase Definition revision is never edited after execution starts.
. An Event and Intervention are never rewritten.
. Every retry creates a new Phase Attempt.
. Every revision creates a new Phase Definition revision and attempt.
. Superseded downstream attempts remain inspectable.
. A Task is deleted only through its explicit delete operation.

== Execution operations

=== Comment

Persist the Intervention without scheduling work. Available for every Event, Artifact, and Phase Attempt.

=== Steer

Deliver a message to a running Agent after its current assistant turn and tool calls finish. Steering is the default when the selected Event belongs to the currently running Agent attempt.

The Intervention must be committed before delivery to the harness. Delivery status is recorded as `queued`, `delivered`, `applied`, or `failed`.

=== Follow up

Deliver a message after the running Agent settles. This remains an explicit secondary action rather than the default.

=== Retry exact

Create a new attempt from the selected attempt's input Workspace Snapshot, using the same Phase Definition revision and captured inputs. Partial output from the selected attempt is not included.

=== Revise and retry

Create a new Phase Definition revision from the selected attempt's input Workspace Snapshot. The user message is appended as an instruction amendment. Factory-owned Agent configuration remains unchanged.

=== Continue repair

Create a configured Builder repair phase from the selected attempt's output Workspace Snapshot. This preserves partial repository changes and supplies the failure evidence plus user message to the Builder.

A deterministic check is never converted into an Agent verdict. After repair, the unchanged check definition runs again. Downstream review also runs again.

== Event addressing

The UI may attach a message to any displayed Event. The server resolves:

[source,text]
----
Event -> Phase Attempt -> Phase Definition -> Execution Branch
----

The selected Event provides context and lineage. The operation always applies to its owning attempt or artifact, never to a raw stream record in isolation.

Each Event response includes server-computed available actions. The UI does not duplicate transition policy.

Examples:

* Running Agent event: `comment`, `steer`, `follow_up`
* Failed Agent event: `comment`, `retry`, `revise`, `repair`
* Failed check event: `comment`, `retry`, `repair`
* Successful historical event: `comment`, `retry`, `revise`
* Plan-with-questions artifact: `comment`, `revise`
* Completed Task event: `comment`, `retry`, `revise`, `repair` when applicable

== Branch and Task behavior

A Task has one selected branch head. Task state is a projection of that branch.

Creating a Task creates its secure Task Workspace before returning success. Task creation and workspace allocation are one coordinated operation: a database failure removes the new workspace, while a workspace failure prevents the Task record. The Task response includes `workspace_path`. Repository preparation materializes isolated repository state beneath this workspace before the first executable phase.

When an Intervention retries historical work:

. Resolve the target attempt and its input or output snapshot.
. Create a child Execution Branch.
. Persist the Intervention and queued attempt atomically.
. Select the child branch as the Task head.
. Mark affected downstream attempts as superseded on the new branch without changing their historical records.
. Recompute Task state from the new head.
. Execute the new attempt and required downstream phases.

Retrying a completed Task reopens that Task. Its prior completed branch and completion evidence remain immutable and visible. The Task's current `ended_at` is cleared, while completion history remains on the prior branch. The one-active-Task rule is enforced before reopening.

A new upstream result invalidates downstream work on the selected branch. The transition policy schedules downstream phases in dependency order. No previous result is silently reused as fresh acceptance evidence.

== Workspace snapshots

Each attempt uses an isolated workspace materialized from an immutable Workspace Snapshot.

[source,text]
----
tasks/<task-id>/
  task.json
  events.jsonl
  workspace/
    snapshots/<digest>/
    branches/<branch-id>/
    attempts/<attempt-id>/
      repository/
      inputs.json
      events.jsonl
      artifacts/
      sessions/
----

Snapshots preserve repository-relative paths, file contents, executable modes, symlinks, tracked files, and relevant untracked files. Git metadata is not part of snapshot content.

Snapshot rules:

* Retry exact materializes the selected attempt's input snapshot.
* Revise and retry materializes the selected attempt's input snapshot.
* Continue repair materializes the selected attempt's output snapshot.
* Successful repository-changing attempts produce a new output snapshot.
* Read-only attempts reference the unchanged input snapshot.
* Snapshot identity is a content digest.
* Snapshots and attempt workspaces remain until Task deletion.

== Planner feedback

Planner questions use the generic Intervention path rather than a Planner-only feedback mechanism.

[source,text]
----
Planner attempt 1
  -> Plan artifact v1 with unresolved questions
  -> User message anchored to the plan artifact or its completion Event
  -> Planner definition revision 2
  -> Planner attempt 2
  -> Plan artifact v2
  -> Approval bound to the v2 digest
----

The revised attempt receives the prior plan, unresolved questions, and Intervention explicitly. Agent Session context is supporting evidence, not the sole source of revision input.

Approval remains unavailable while the selected plan has unresolved questions.

== Failed-step repair

[source,text]
----
Check attempt 1 fails
  -> User sends repair instruction
  -> Builder repair attempt starts from the failed output snapshot
  -> Check attempt 2 executes the unchanged check definition
  -> Reviewer executes against the repaired branch
----

For an Agent failure:

* Retry exact discards partial output and starts from the input snapshot.
* Revise and retry discards partial output and adds the message to a new definition revision.
* Continue repair keeps partial output and asks the configured Builder to repair it.

The user supplies only the message. Factory policy chooses the configured Agent role and immutable Task configuration.

== Harness seam

The Harness module owns Agent process interaction behind a small interface:

[source,go]
----
type Harness interface {
    Start(context.Context, AttemptRequest, EventSink) (Execution, error)
}

type Execution interface {
    Send(context.Context, Message) error
    Wait(context.Context) (Result, error)
    Abort(context.Context) error
}
----

`AttemptRequest` contains the immutable attempt inputs and Agent Session starting coordinate. `Message` contains persisted Intervention identity, text, and delivery mode.

The Pi adapter runs the installed `pi` command in RPC mode. RPC provides:

* steering and follow-up delivery
* abort support
* streamed lifecycle and tool events
* append-only session entries with durable entry IDs
* session tree inspection and branching

Each Agent attempt records its base session entry ID and resulting leaf entry ID. Revised attempts branch from the recorded base coordinate instead of appending to a contaminated active path.

Harness-specific RPC details do not leak into factory orchestration or HTTP handlers.

== Transition policy

The transition-policy module decides available operations and downstream scheduling from durable facts.

Inputs:

* Task state and selected branch
* target Phase Definition and Attempt
* target Event or Artifact
* attempt status and executor kind
* dependency and acceptance state
* active process state
* Intervention intent

Outputs:

* accepted or rejected command
* branch operation
* snapshot starting point
* Phase Definition revision, when required
* next queued attempts
* projected Task state

Required checks remain mandatory. No Intervention waives a required check, protected-path violation, malformed envelope, or inconsistent review verdict.

== HTTP interface

All UI and HTTP resources use `tasks`; legacy resource naming is not retained as an alias.

=== Create a Task

[source,http]
----
POST /api/v1/tasks
----

Task creation allocates the Task Workspace and returns its `workspace_path`. A successful response always identifies an existing private workspace.

=== Submit an Intervention

[source,http]
----
POST /api/v1/tasks/{task-id}/interventions
----

[source,json]
----
{
  "target": {
    "artifact_id": "artifact-id",
    "anchor": {
      "kind": "text_range",
      "start": 418,
      "end": 449,
      "quote": "Proposed End State Architecture"
    }
  },
  "intent": "revise",
  "message": "This section must cover Task drafts.",
  "expected_branch_head": "attempt-id",
  "idempotency_key": "client-generated-id"
}
----

`target` accepts exactly one of `event_id`, `artifact_id`, or `attempt_id`. An Artifact target may include one canonical `anchor`. The server verifies that the Artifact digest and quoted content still match before accepting the Intervention; stale anchors return `409 stale_anchor`.

`intent` accepts:

* `comment`
* `steer`
* `follow_up`
* `retry`
* `revise`
* `repair`

`delivery` defaults to `steer` for a running Agent and is rejected when it does not apply. Non-comment execution intents require a non-empty message except exact retry.

The response contains the persisted Intervention, normalized target and anchor, chosen policy action, branch ID, and queued attempt ID when execution is scheduled.

=== Reads

Add:

* `GET /tasks/{id}/branches`
* `GET /tasks/{id}/attempts`
* `GET /tasks/{id}/attempts/{attempt-id}`
* `GET /tasks/{id}/artifacts`
* `GET /tasks/{id}/interventions`

Events include `attempt_id`, optional `artifact_id`, available actions, and branch lineage.

=== Concurrency

Mutation requests require:

* mutation token
* same-origin validation
* client-generated idempotency key
* expected selected branch head

A stale head returns `409 stale_branch`. Reusing an idempotency key returns the original result without creating duplicate attempts.

Persisting the Intervention, creating its branch, queuing its attempt, and selecting the new branch occur in one database transaction.

== Persistence model

Replace the database schema outright with:

tasks:: Task identity, Task Workspace path, selected branch, projected state, repository source, timestamps, usage, and cost.

branches:: Parent branch, fork attempt, selected head attempt, status, and timestamps.

phase_definitions:: Stable phase key, revision, executor kind, owner, specification JSON, digest, and parent revision.

phase_attempts:: Definition revision, branch, attempt number, snapshots, status, error, process, Agent Session coordinates, usage, and timestamps.

interventions:: Target coordinates, optional canonical Artifact Anchor, actor, intent, text, delivery state, idempotency key, expected branch head, and timestamps.

artifacts:: Attempt output type, digest, metadata, storage path, and timestamps.

events:: Sequence cursor, attempt and artifact coordinates, parent Event, type, payload, and timestamps.

processes:: Attempt process identity, kind, PID, command, status, exit code, and timestamps.

agent_sessions:: Attempt and role, harness, provider, model, settings, session path, base entry, result leaf, usage, and cost.

workspace_snapshots:: Digest, manifest, storage path, size, and timestamps.

Foreign keys cascade only during explicit Task deletion. Historical branch records are otherwise immutable.

== Recovery

On restart:

. Mark running processes ended or failed after identity-safe recovery.
. Mark their attempts `interrupted`.
. Preserve their last output snapshot when safely capturable.
. Move the selected branch and Task to `blocked`.
. Offer retry, revise, or repair actions based on the interrupted attempt.
. Never resume automatically.

Queued but unstarted attempts remain queued only when no external process began. The user explicitly resumes execution.

=== Artifact rail and viewer

The Artifact experience follows the second reference:

* Top-level `Artifacts` and `Summary` modes occupy the contextual rail/viewer area. Auto-advance is a toggle, not a separate data model.
* The Artifact picker groups immutable versions by type, Phase Definition, attempt, and branch.

=== Anchored contextual composer

Selecting Artifact text, a rendered block, an Event row, or a state-graph node opens a compact composer adjacent to the target, like the second reference. The selected source range or node remains visibly highlighted while the composer is open.

The composer shows:

* immutable target label and digest
* phase, attempt, branch, and definition revision
* input/output Workspace Snapshot identity
* server-provided valid actions
* concise consequence preview
* message field
* default action and Send control

Artifact text selection is converted to an Artifact Anchor before opening the composer. Supported anchor kinds are:

* `text_range`: UTF-8 source offsets plus exact quote
* `line_range`: source line start/end plus exact quote
* `json_pointer`: RFC 6901 pointer plus value digest
* `block`: renderer block identity plus source range

Rendered DOM paths, pixel positions, and client-only node indexes are never persisted. If selection cannot map to canonical source, the composer targets the whole Artifact and states that reduced precision.

Submitting a comment stores the anchor without scheduling work. Submitting a state-changing action stores the same anchor as instruction context, then creates the policy-selected definition revision, attempt, or branch.

=== State-changing actions

The UI never directly writes a Task or Attempt status. It renders server-provided `available_actions`; selecting one previews the append-only transition before submission.

[cols="1,2,2",options="header"]
|===
|Selected state/target
|Typical actions
|Visible result

|Draft Task
|start, comment
|First branch and queued preparation attempt

|Running Agent Attempt
|comment, steer, follow-up, pause, abort
|Delivery status beside the anchored Intervention

|Running deterministic Attempt
|comment, pause, abort
|No Agent steering action

|Failed or interrupted Agent Attempt
|comment, retry exact, revise and retry, continue repair
|New branch/attempt and explicit input or output snapshot source

|Failed deterministic check
|comment, retry exact, continue repair
|New check attempt or Builder repair followed by the unchanged check

|Successful historical Attempt or Artifact
|comment, retry exact, revise and retry
|Child branch; replaced downstream work shown as superseded

|Completed Task
|comment, retry exact, revise and retry, continue repair when applicable
|Reopened Task after active-slot validation; completed branch retained
|===

The table documents expected policy categories only. The transition-policy module remains authoritative and may remove invalid actions. The composer does not infer actions from status strings.

After submission, the UI:

. Keeps the old Attempt and Artifact visible as immutable history.
. Adds the Intervention at its anchor with `queued`, `delivered`, `applied`, or `failed` state.
. Draws the new child branch and queued Attempt in the state graph.
. Selects the new branch only after the server transaction succeeds.
. Marks invalidated downstream Attempts as superseded on that branch.
. Moves live focus to the new Attempt while preserving a route back to the source anchor.

A stale branch or anchor leaves the composer text intact, refreshes lineage, and requires the user to reselect the action. A completed-Task retry warns that the Task will reopen and consume the single active-Task slot.

=== Trace and lineage presentation

Every Attempt and relevant Artifact displays:

* attempt number and definition revision

== Framework-neutral style seam

The style system is a deep module. Its interface is a small set of semantic CSS custom properties, classes, data attributes, ARIA states, and documented DOM relationships. Vue is one adapter at this seam; another framework can emit the same markup contract and reuse the implementation unchanged.
